# Shared Channels Design System v2 · rebuild plan

## Decision (21 October 2026)

The "Native" visual direction is retired. v2 rebuilds the `sc-` library from the ground up in the language of direction E, "Dubai Design System, evolved". That direction is in Paper file 01M5A0E3KTNXQ1262CTCJDXCMP, page p-6-0, artboards E0–E4.

- **Not reused:** we do not use the `dda-` components or their code. v2 is our own Stencil library with the `sc-` prefix. Only the visual language is taken from DDS.
- **Requirements:**
  - every colour in OKLAB
  - no DDS teal, or anything close to it
  - WCAG 2.2 AA as the floor, aiming above it where cheap
  - optimised: smaller bundles, less CSS duplicated across shadow roots, no runtime cost for theming
  - Arabic and English as equals
  - theming by channel, with entities getting attribution only
  - Latin digits in Arabic
  - motion from Emil Kowalski's skills, using the duration rule of thumb (micro-interactions 100–150ms, standard 150–250ms, modals and drawers 200–300ms, exits about 20% faster than entrances)
- **What carries over from v1:**
  - the behaviour, accessibility and API lessons in Standard 2.0 (`docs/shared-channels-ux-standard.md`) and `docs/library-conformance.md`
  - the specs in `components/specs/`
  - the test suites, as a regression baseline
  - the Dubai Now reference work: the page inventory, the audit and the pattern candidates

  The look does not carry over.

## The direction E language, in short

- **Colour:**
  - **City indigo** is the shared primary. It replaces DDS teal and carries what all channels share: the network strip, sign-in and Dubai Pay hand-offs.
  - **Seven channel signatures** are tonal palettes in the DDS and Material manner:
    - tone 40 for actions, with white text
    - tones 90 and 95 for containers and tints
    - tone 80 for actions in dark mode, with neutral-10 text
  - **Neutrals:** a tonal ramp (10, 30, 40, 80, 90, 96, 100). Neutral-90 is for dividers only, never for a control edge.
  - **Semantic colours** (error, success, warning, info): tone 40 on a tone-95 container.
- **Shape:** 4px for controls, 8px for fields, 12px for cards, 6px for status chips. Surfaces are flat. Elevation is minimal.
- **Type:** Dubai Font in one family for both scripts, on the DDS Material scale. Arabic runs one step larger with taller leading. Body text is 18px in English and 20px in Arabic.
- **Accessibility fixes over DDS:**
  - control boundaries are 1.5px neutral-40, which passes 3:1, where DDS used 1px neutral-90 at 1.29:1
  - primary controls are 56px high
  - the focus ring is 3px with a 2px offset
  - status is never shown by colour alone: an icon plus text
- **Signature components:** the stepper (28px markers, a check on completed steps, a halo on the current one), outlined fields, underlined links, status chips, and the Dubai Now home layout on E1.

## Waves

Every code agent works in its own git worktree on its own branch, cut from the integration branch `v2`. The coordinator merges each branch back into `v2`. `main` and the live site keep v1 until v2 passes Wave 4 and the user approves the switch.

Paper work goes into a NEW file, "Shared Channels · Design System v2". The v1 file stays untouched as a record.

### Wave 1 · foundations (3 agents in parallel)

1. **F1 · Foundations and tokens:**
   - writes `docs/v2/foundations.md`, the single source of truth for colour, type, shape, space, elevation, focus, motion and layout
   - implements the tokens in `tokens/*.json` (DTCG, OKLAB), with tonal palettes generated by a script
   - extends the checks: contrast for every role pair, teal band, no hex
   - covers dark mode at the token level
2. **F2 · Language and component audit:**
   - reads direction E (E0–E4) and the DDS repository's component anatomy for reference only
   - writes `docs/v2/component-language.md`: per-component visual rules for every current `sc-` component and every planned new one (anatomy, sizes, states, RTL)
3. **F3 · Architecture and performance:**
   - audits v1's build: bundle sizes, CSS duplicated per shadow root, shared styles, lazy loading, font loading, type-role generation
   - writes `docs/v2/architecture.md`: target bundle budgets, how shared styles are loaded (constructable stylesheets and adoptedStyleSheets), whether each component uses shadow DOM, scoped styles or light DOM, a token delivery strategy, and a testing and CI plan

### Wave 2 · build (about 9 agents in parallel)

- **C1–C5 · Components by family:**
  - C1: actions and navigation, including the new chrome
  - C2: form fields
  - C3: feedback and status
  - C4: content and layout
  - C5: the new content components (attention card, module card, tile, empty state, accordion, timeline, notification list, filter chips, modal)

  Each family is rebuilt to `foundations.md`, `component-language.md` and `architecture.md`, with tests, EN and AR playground pages, and specs.
- **P1–P3 · Paper boards** in the v2 file:
  - P1: foundations
  - P2 and P3: component spec boards, split by family
- **S1 · Standard:** rewrites the visual-foundations chapter (8) and every Native-specific passage of Standard 2.0 to v2. All motion rules stay as they are.

### Wave 3 · reference (4 agents)

- **R1 and R2:** redesign the Dubai Now public and signed-in pages in Paper, in the v2 language.
- **R3:** builds the Dubai Now reference site from the v2 components.
- **R4:** runs the second-channel test, Visit Dubai, using only the templates and a channel configuration file.

### Wave 4 · quality (4 agents, then merge)

- **Q1:** accessibility (axe, keyboard, screen reader semantics, contrast, forced colours, zoom to 400%)
- **Q2:** Arabic and RTL parity
- **Q3:** performance against the budgets
- **Q4:** a design review of code against Paper

The coordinator then merges `v2` and asks the user to approve replacing v1 on `main` and the live site.
